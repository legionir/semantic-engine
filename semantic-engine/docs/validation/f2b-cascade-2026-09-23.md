## Method: v2 preload probe + three overlap scripts

`evidence-f2b-cascade-2026-09-23/f2b-v2.cjs` (test-only preload, not part of
`npm test`) counts console API traffic, logs every 429/409/4xx with timestamps,
logs `/api/state` poll outcomes (`status/pending/gitReport` vs `ERROR 429`),
times every `git status --short --branch` subprocess, reports per-test API deltas,
and observes the server-side `RateLimiter` (patched prototype, same cached module).
Controlled knobs (experiments only, clearly labelled): `F2B_LIMIT_OVERRIDE`,
`F2B_MODEL_DELAY_MS` (delays `/chat/completions` responses — a proxy for slow
tasks), `F2B_GIT_DELAY_MS` (delays every git-report callback).

`f2b-overlap.cjs` / `f2b-overlap-task.cjs` / `f2b-overlap-session.cjs` are minimal
standalone scripts (same runtime/server/stub setup as `web.test.js`) that
deterministically test clear / new-task / new-session issued inside the
done-but-git-pending window. They hardcode this sandbox's `REPO_ROOT`; on another
checkout adjust that one line (behaviour is otherwise path-independent; `f2b-v2.cjs`
itself resolves `Middleware.js` cwd-relative first).

Quirk (log label only, counts unaffected): with `F2B_GIT_DELAY_MS>0` the two git
completions in Exp7 both print `#2`, because the counter is incremented at
subprocess completion but the label is printed at delayed release. Summary counts
(`launches/completions`) are correct.

## Finding 1 — rate-limiter cascade: mechanism PROVEN, historical cause UNPROVEN

- #3 proves exhaustion **can** produce the exact historical signature (10/28,
  timeouts + 429 asserts, wall ~70–86s).
- #4/#6 prove realistic slowdown exhausts the **production** limit 120 (green
  101 → 494/699; state polls 35 → 433/640). Each 8s `waitFor` at 50ms is ~160
  polls; denied requests increment the fixed-window counter too, so once over
  the limit every further poll is a 429 until the 60s reset (recovery observed
  in #6 for #25–28).
- #5 (control) proves the limiter is **necessary** for the late cascade under
  the same slowdown: disabling it moves 20/28→27/28 and 42.5s→8.6s with `429=0`.
- `waitFor` treats a 429 body (`{error}` — no `status`) as “not ready” and keeps
  polling, turning one slow task into a poll storm. The suite has no 429
  handling (neither backoff nor fail-fast).
- **Not proven:** that the historical 10/28 (limit 120, no artificial knobs) was
  caused by the limiter. Natural reproduction with limit 120 yielded 20–21/28,
  never 10/28; 10/28 required the artificial limit 30; no historical log records
  429 counts. The limiter is a **confirmed fragility** (margin 19), not a proven
  historical cause. The 10/28 pattern in #3 is first-10-pass/rest-fail; the
  historical pass/fail positions are unknown.

## Finding 2 — stale `run:status` race: PROVEN under slowdown

In #4, delegation (#13) finished in **92ms with its wait satisfied**, yet its own
task needs ≥600ms (3 model calls × 200ms) and demonstrably finished later (git at
+5182ms, `FINAL … aggregated` printed **after** the FAIL). Therefore the
`run:status done` the wait matched **cannot be its own** — it is stale, from the
previous task. Consequences observed: the orphaned background task makes #14’s
`POST /api/clear → 409`, #14 times out after 8s, and #14 never resets
`MAX_ITERATIONS` (→ #23 fails `41 == undefined`). Same shape in #6 (#13 77ms).
Root: API waits for `done` return **before** `run:status` is emitted (done is set
before `finally`; `run:status` after git+flush+save), so the next SSE test can
attach before the previous `run:status` arrives. Natural occurrence (no knobs) was
not observed — green runs show `run:status` before the next attach — so this stays
a proven-under-slowdown race, timing-sensitive at the millisecond level (#5 with
the same delay did not trigger it).

## Finding 3 — finally overlap: HARM PROVEN for clear, task, and session

Code (`structured-ai/web/server/ServerImplementation.js`): `startTask` sets
`state.status` to `done`/`failed`/`cancelled` in `try`/`catch` **before** `finally`
awaits `recordGitReport()` (git timeout 8000ms, then `git:report` + message),
`eventstore.flush()`, auto-continue scheduling, approval denial, `run:status`
emission, and `saveSession()`. Busy guards on `POST /api/clear`, `/api/sessions`,
`/api/sessions/:id`, `/api/tasks` (plus discussion checks) test only
`state.status === "running"` — the post-`done`/in-`finally` window is not busy.

- **Natural window observed:** #4/#10 poll saw `status=done, gitReport=false` at
  +3848ms; git completed +3851ms; the test finished +3850ms — before git.
- **Exp 7–9 prove harm deterministically** (2000ms git delay widens the natural
  window; guards allow all three operations mid-window with 200/202/201):
  clear → new session gains the old `git-report` message+event; new task → old
  git misattributed to the new `turn_id` (`state.currentTurnId` overwritten) and
  misordered after the new turn; new session → same pollution as clear.
- Contracts are silent: `docs/contracts/shared-invariants.md`,
  `structured-ai/test/contracts/api.contract.test.js`, and
  `test/fixtures/api-surface.json` define neither “done means finalization
  complete” nor “done implies git-report present”. SSE (`run:status`) and
  `GET /api/state` (`done`) observe different points; tests are inconsistent
  across them (conversation waits for all three since PR #19; second-task,
  approval honour/denied, and reopen-and-continue still wait only for `done` —
  untouched here for lack of new failing assertions).

**Git-report cwd: code-proven wrong key (side finding, not fixed).**
`RuntimeContextBuilder.build()` exposes the root at `.runtime.workspace_root`
(and `.workspace.root`) — there is **no** top-level `.workspace_root`. The same
`ServerImplementation.js` reads it correctly in `snapshot()`
(`context.runtime.workspace_root`) but `recordGitReport()` reads the top-level
`.workspace_root` → `undefined` → `execFile` falls back to `process.cwd()` → the
repo checkout. Corroborated at runtime by Exp 7–9 (branch `arena/…`, text
`0 files changed…` instead of `not a git repository`, which is what the temp
workspace would yield). Consequence: naively “fixing” the key would break the
conversation test’s `/file/` assertion on `gitReport.content` (a non-repo temp dir
yields `not a git repository`, which contains no `file`), so the current accidental
behaviour is load-bearing. The question “which directory SHOULD git-report
reflect?” belongs to the RV-6 contract decision — untouched here.
