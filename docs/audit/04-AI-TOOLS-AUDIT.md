# بررسی خروجی هر لایه: آیا اطلاعات کامل، کافی و درست به AI می‌رسد؟

روش: روی fixture پروژه (۵۸ فایل، ۲۰۵ symbol) یک سرور MCP واقعی (SDK، transport درون‌حافظه) بالا آمد و همهٔ ۳۸ ابزار
(۳۲ پیش‌فرض + edit + experimental) از طریق `tools/list` و `tools/call` صدا زده شدند؛ علاوه بر مسیر موفق، ورودی نامعتبر،
شناسهٔ ناموجود، پارامتر غلط‌املایی و مسیر خارج از پروژه هم امتحان شد. نتیجهٔ هر لایه قبل و بعد از اصلاح ثبت شده است.

**محدودیت روش:** یک fixture و یک اجرا؛ با مدل زبانی واقعی سنجیده نشد که چقدر درست از ابزارها استفاده می‌کند. ابزارهای
`edit_*` و experimental فقط از نظر schema و توضیح بازبینی شدند و روی داده اجرا نشدند (تست‌های موجود خودشان را می‌پوشانند).

## لایه ۱ — داده‌ی ایندکس (`project-index.json`)
| سؤال | حکم |
|---|---|
| کامل؟ | **بله.** فایل، symbol (امضا، خط شروع/پایان، visibility، complexity)، گراف import/call/type، `languageSupport` برای هر زبان، `diagnosticsRun` |
| درست؟ | **بله، با صداقت نسبت به اطمینان:** هر یال `provenance` (extractor, basis, confidence) دارد؛ یال حدسی از قطعی جداست |
| کافی؟ | بله. کمبود شناخته‌شده: ۰ بردار (embedding) وقتی `--no-vectors` است؛ در این حالت `semantic_search` صریحاً `keyword-only` می‌شود |

## لایه ۲ — پیاده‌سازی ابزارها (محتوای `items` / `metadata`)
| ابزار | یافته پیش از اصلاح | وضعیت |
|---|---|---|
| `search_text` | `items[].line` همیشه `1` بود؛ خط واقعی فقط در `metadata.line` — AI به خط اشتباه می‌رفت | **رفع شد** (`line` = خط واقعی) |
| `impact_analysis` | id ناموجود → `success:true` و لیست خالی = «هیچ‌چیز تأثیر نمی‌پذیرد» | **رفع شد** → `success:false` با راهنمای یافتن id |
| `get_git_hotspots` | `metadata.hotspots[].linesAdded/linesDeleted = 0` ساختگی؛ لیست خالی بدون دلیل | **رفع شد** (`null` + `note`) |
| `get_recent_changes` | پروژه‌ای که زیرپوشهٔ یک مخزن بزرگ‌تر است تاریخچهٔ **کل مخزن** را می‌گرفت (روی fixture، commitهای همین مخزن)؛ عنوان commit دارای `\|` نویسنده/تاریخ را جابه‌جا می‌کرد | **رفع شد** (`-- .` و جداکنندهٔ `\x1f`) |
| `find_tests` | نتیجهٔ خالی بدون توضیح، قابل‌خواندن به‌عنوان «تست ندارد» | **رفع شد** (`metadata.note`) |
| `diagnostics_get`, `semantic_search`, `code_read`, `explain_symbol`, `get_file_summary`, `simulate_mutation`, `detect_architecture_violations`, `structural_search` | — | **درست و صادق** (هشدار «خالی ≠ تمیز»، `degradedReason`، `truncated`، handle وابسته به نسخهٔ فایل) |
| ابزارهای `symbol_find`, `code_outline`, `project_*`, `gains_report` | — | درست؛ `gains_report` تخمین از تعداد خط است و همین را در توضیح می‌گوید |

## لایه ۳ — Registry و اعتبارسنجی ورودی (آنچه AI از schema می‌بیند)
| سؤال | قبل | بعد |
|---|---|---|
| پارامترهای دارای توضیح | **۴۶ از ۱۳۳ (۳۵٪)** | **۱۳۳ از ۱۳۳** |
| توضیح خروجی و «کِی از این ابزار استفاده کنم» | وجود نداشت؛ توضیح ابزارها ۴۷–۳۳۱ نویسه | هر ابزار: کاربرد، جایگزین مناسب، شکل خروجی، فیلدهایی که معنای نتیجه را عوض می‌کنند |
| `edit_plan.edits` | `items: {type: object}` — AI نمی‌توانست بداند `path/start/end/replacement/expectedHash` لازم است | schema کامل با `required` |
| پارامتر غلط‌املایی (`limt`) | بی‌صدا نادیده گرفته می‌شد؛ پاسخ طوری بود که انگار اعمال شده | `metadata.warnings` + پیشنهاد «did you mean `limit`» |
| پیام‌های خطای اعتبارسنجی | روشن (`limit: must be integer`, `direction: must be one of …`) | بدون تغییر — **درست و کافی** |
| `code_fold.level`، `structural_search.ruleId`، `structural_rule_test` | معنا از نام قابل‌حدس نبود (و `ruleId` برخلاف انتظار فقط برچسب است) | با خواندن کد مستند شد |
| هزینهٔ زمینه | `tools/list` پیش‌فرض ≈ ۱۴ هزار نویسه | ≈ ۳۱ هزار نویسه (~۷٫۷k توکن): **هزینهٔ آگاهانه**، برای دقت بالاتر انتخاب ابزار و پارامتر |

سند توضیحات یک‌جا (`src/ai/tools/toolDocs.ts`) نگه داشته می‌شود و تست `toolDocs.test.ts` اگر ابزار یا پارامتر جدیدی بدون توضیح
اضافه شود، CI را قرمز می‌کند؛ همین متن `docs/AI-TOOLS.md` و skill را تولید می‌کند و تست مطابقت فایل‌ها را می‌سنجد.

## لایه ۴ — پاکت MCP (`tools/call`)
| سؤال | حکم |
|---|---|
| ساختار | `content[0].text` = JSON خروجی، `structuredContent` = همان به‌علاوهٔ `projectId` و `indexGeneration`، `isError = !success` — **درست و سازگار** |
| `initialize` | سرور تک‌پروژه هیچ `instructions` نداشت؛ **اضافه شد** (راه شروع، ترتیب ابزارها، نحوهٔ خواندن `truncated`/خالی/`warnings`) و در Gateway هم الحاق شد |
| نقص باقی‌مانده | payload دو بار فرستاده می‌شود (متن + structured) → برای کلاینتی که هر دو را وارد context کند دو برابر توکن. تغییرش با قرارداد مصرف‌کننده‌ها (structured-ai) تداخل دارد، پس دست نخورد |

## لایه ۵ — Gateway (چندپروژه‌ای)
- `tools/list` از اولین worker آماده گرفته و ۶۰ ثانیه کش می‌شود و پارامتر `project` به همهٔ ابزارها اضافه می‌شود؛ توضیحات تازه از همین مسیر عبور می‌کنند (تست `GatewayMcp` سبز).
- `list_projects` وضعیت (`state`) هر پروژه را می‌دهد؛ پروژهٔ ناشناس پاسخ «Known projects: …» می‌گیرد — **کافی و قابل اصلاح توسط AI**.
- نقص باقی‌مانده: بدون worker آماده فقط `list_projects` دیده می‌شود (مستند در OPEN-ITEMS).

## لایه ۶ — skill و مستندات
`skills/semantic-engine/SKILL.md` (قابل‌نصب با `npm run install:skill`) و `docs/AI-TOOLS.md` از registry تولید می‌شوند: لیست کامل ابزارها با
کاربرد، نوع/الزامی‌بودن/محدودهٔ هر پارامتر و شکل خروجی، به‌علاوهٔ راهنمای اتصال، گردش‌کار و قواعد خواندن نتیجه.

## پیشنهادهای باز (بدون تغییر)
1. ابزارهای `edit_*` در `tools/list` دیده می‌شوند حتی وقتی خاموش‌اند (پاسخ `DISABLED`)؛ پنهان‌کردنشان قرارداد فعلی را عوض می‌کند. فعلاً در توضیح ذکر شده.
2. `explain_symbol` و چند ابزار دیگر «یکی از id/name» را فقط در زمان اجرا می‌سنجند، نه در schema.
3. خطاهای `code_read` کوتاه‌اند (`NOT_FOUND: source file`) و نمی‌گویند مسیر نسبت به چه چیزی سنجیده شد.
4. ارزیابی با مدل واقعی (چند وظیفهٔ نمونه، شمارش فراخوانی‌های بی‌فایده) انجام نشده و برای سنجش واقعی «کافی بودن» لازم است.
